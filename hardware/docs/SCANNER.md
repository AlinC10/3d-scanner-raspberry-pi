# Scanner Hardware Controller (`../scanner.py`)

The `Scanner` class in `../scanner.py` is the central hardware abstraction layer and real-time physical orchestrator of the 3D scanner rig. 

It manages the lifecycle of the stepper motors, safety limit switches, high-power illumination LEDs, stereoscopic camera feeds, and background cloud uploads. It is engineered specifically for thread-safe, non-blocking operation inside multi-threaded asynchronous servers (such as FastAPI).

---

## 🏗️ Architectural Pillars

```
                     ┌───────────────────────────────────────────────┐
                     │          Scanner Singleton Instance           │
                     └───────┬──────────────┬──────────────┬─────────┘
                             │              │              │
                ┌────────────┴───┐   ┌──────┴─────┐  ┌─────┴─────────────────────┐
                │ Stepper Motors │   │ Endstops   │  │ BaseDualCamera Hierarchy  │
                │ Turntable/Z    │   │ Up / Down  │  │ DualCameraRPISync (rpi.sync)│
                └────────────────┘   └────────────┘  │ DualCameraXVS (xvs)       │
                                                     │ DualCamera (staggered)    │
                                                     └─────────────┬─────────────┘
                                                                   │
                                                     ┌─────────────┴─────────────┐
                                                     │ Parallel Upload Pipeline  │
                                                     │ Queue + Drain -> R2       │
                                                     └───────────────────────────┘
```

1. **Non-Blocking Lock Scoping**: Mutex locks (`self._lock`) are acquired *only* for state validation and microsecond-level state transitions. Long-running mechanical loops run strictly **outside** the lock, ensuring API requests like `/status` and `/cancel` are processed with zero latency.
2. **Cooperative Thread Cancellation**: Instead of forcefully terminating Python threads, a `threading.Event()` (`self._cancel_event`) is checked at every critical hardware boundary (before each rotational stop, photo trigger, and Z-axis lift).
3. **Producer-Consumer Background Uploads**: Capturing images and uploading to Cloudflare R2 are decoupled through an asynchronous worker queue (per-file retry with backoff, parking of failing files, a progress-based drain deadline and a final bucket verification against a manifest; see "Upload pipeline" below). The capture thread never waits for an upload.
4. **Hardware Safety Interrupts**: Both limit switches are wired to `motor.stop()`, but only act while a Z move is in flight (`_z_moving` flag set by `move_z_up`/`move_z_down`); a press while Z is idle is ignored, because the `0xFF` stop is universal and would abort the turntable or cut every motor. Because motor steps are generated by the Arduino, calling `stop()` instantly injects the out-of-band `0xFF` universal abort byte over UART, halting the hardware stepping loop in $\le 1.0\text{ ms}$ without waiting for Python interpreter cycles.
5. **Exclusive Motion (`motion_guard()`)**: Every physical move (`move_z_up`/`move_z_down` and everything built on them, `home_z_axis`, `move_z_to_top`, the turntable rotation of a ring, and the `/test` moves) runs inside `with scanner.motion_guard():`. The guard is **non-blocking**: if another thread already holds it, it raises `ScannerBusyError` (a `ScannerError`; the `/test` router maps it to `409`) and nothing is sent to the Arduino. It is re-entrant for the owning thread, so the helpers nest freely inside one `scan()`. Without it two overlapping Z moves would share the `_z_moving` flag and the single STOP budget, and the first one to end would silently remove the endstop protection of the other.
6. **Mechanical Settling Hold**: Stepper coil de-energization (`disable()`) is preceded by a 0.5-second pause (`settle_delay`, interruptible by a cancel) during which the coils keep holding the rotor. Cutting the current while the platter or carriage still carries kinetic energy lets it coast past the target. (An electrical benefit, i.e. avoiding back-EMF transients on the shared 12 V bus that were suspected of resetting the Arduino, is an unverified hypothesis; the Arduino now recovers from a reset by itself.)

## 🚦 State Machine (`ScannerState`)

The scanner enforces strict lifecycle state transitions:

```
  IDLE ──────────► PREPARING ──────────► PREPARED ──────────► RUNNING
    ▲                  │                    │                   │
    │                  ▼                    ▼                   ▼
    │              CANCELLED            CANCELLED           PROCESSING
    │                  ▲                    ▲                   │
    │                  │                    │                   ▼
    │               ERROR                ERROR             DOWNLOADING
    │                  ▲                    ▲                   │
    │                  │                    │                   ▼
    └──────────────────┴────────────────────┴────────────── COMPLETED
```

* **`PREPARE_ALLOWED = ("idle", "completed", "cancelled", "error")`**: Allows re-preparing after a finished or aborted run without requiring an application restart.
* **`TERMINAL = ("completed", "cancelled", "error")`**: Preserved by `cleanup()` so API consumers and frontend polling loops can read the final run outcome without having it prematurely overwritten back to `IDLE`.
* **`_stopping` flag**: Raised by `emergency_stop()` (after it has published `CANCELLED`, under `_lock`) and cleared in its `finally`. While it is set, `setup_and_stream()` refuses a new `/prepare` with `ScannerStoppingError` (a `RuntimeError`, `conflict = True`; the router answers **409**) and `cleanup()` does not touch the state. This is a *mitigation*: a new prepare can no longer clear `_cancel_event` while the old run is still winding down. It is not a per-run token: old threads still share `_cancel_event` and the hardware (a `run_id` per run is the full fix, see `../../plans/implemented/MOTOR_FIXES_PLAN.md` section 7).

## 🎬 Two-Phase Preparation Architecture

To deliver an immediate live video feed to the frontend while accommodating 15–40 seconds of physical carriage travel, preparation is divided into two distinct phases:

### Phase 1: Immediate Stream Startup (`setup_and_stream`)
* **Execution**: Synchronous (duration: ~1.5s).
* **Actions**:
  0. **Preflight** (`preflight()`, before any state change): `r2.preflight()` (credentials, write/read/delete rights), `tof.available`, and at least `MIN_FREE_DISK_MB` (2048) free under `input_images/`. The first failure raises `ScannerPreflightError` (a `RuntimeError`, so the router answers 400 with the message); the state stays `IDLE` and `phase = "error"`, `error = <message>`. `SCAN_PREFLIGHT=0` skips the checks (development only).
  1. Validates state in `PREPARE_ALLOWED` and transitions to `PREPARING`.
  1b. Closes any stale `dual_cameras` (`_close_cameras()`) and calls `lights.unlock_brightness()`, so a second prepare in the same process never meets "device busy" or a frozen dimmer.
  1c. Refuses a brightness of 0 (`ScannerError`) **before** the lights go on and before the bucket is wiped.
  2. Powers ON chamber lights (`lights.on()`).
  3. **Resolves Camera Driver Mode**: Dynamically selects camera implementation based on resolution hierarchy:
     $$\text{call-level } \mathtt{camera\_mode} \longrightarrow \mathtt{kwargs["camera\_mode"]} \longrightarrow \mathtt{self.camera\_mode} \longrightarrow \text{Default: } \mathtt{"rpi\_sync"}$$
     - `"rpi_sync"` / `"sync"`: Instantiates `DualCameraRPISync` (continuous libcamera `rpi.sync`, DMA triple-buffering, spectator-driven on-demand MJPEG encoding).
     - `"xvs"`: Instantiates `DualCameraXVS` (hardware pin Master/Slave frame sync with asymmetric startup).
     - `"staggered"`: Instantiates `DualCamera` (software multi-threading with 0.15s dispatch stagger).
  4. Calls `dual_cameras.prepare_scan(..., keep_running=True)` to initialize the sensor pipeline (AE/AWB are **not** locked yet). The cancel flag is re-checked after the camera construction, after `prepare_scan` and after the stream start: a cancel that landed meanwhile closes the new cameras, switches the lights off and returns `None`.
  5. Boots live streaming:
     - Generates RTSP stream endpoints via `generate_livestream(bitrate)` and stores URLs in `self.stream_urls`.
     - Powers native browser-friendly MJPEG streaming via `/scanner/stream/mjpeg` with zero idle CPU overhead.
  6. **Returns `stream_urls` immediately** to the caller.

### Phase 2: Asynchronous Homing & Auto-Tuning (`finish_preparation`)
* **Execution**: Asynchronous background task (via `FastAPI.BackgroundTasks`).
* **Actions**:
  1. Safely strips out initialization kwargs (`master_id`, `slave_id`, `video_resolution`) to prevent downstream signature errors.
  2. Checks for cancellation (`_cancel_event`) **before the first command**, then moves the carriage down to the bottom endstop (`home_z_axis()`, at most `Z_TRAVEL_MAX_MM + Z_HOMING_MARGIN_MM` = 165 mm = 16500 steps). Incorporates a **0.5-second settling pause** before de-energizing the Z-axis coil (`disable()`); the pause is a mechanical settle, not a verified electrical protection.
  3. Checks for cancellation: `if self._cancel_event.is_set(): return`.
  4. Energizes Z explicitly (`z_axis_motor.enable()`, no reliance on the firmware's auto-enable) and raises the carriage by **+30.0 mm** to rest directly in front of the illuminated object, then releases the driver again.
  5. Re-checks that the brightness is not 0 (the user may have changed it), then cleans the previous scan's assets from the Cloudflare R2 bucket (`r2.delete_all_files_from_bucket()`, paginated, raises on an incomplete cleanup). A failure is a `ScannerError("Cloud sanitization failed: ...")` and ends the preparation in `ERROR` before the cameras are touched. (The local photo directory is wiped at the start of `scan()`.)
  6. (checked in step 5)
  7. **Locks the brightness API** (`self.lights.lock_brightness()`) so operators cannot accidentally dim the lights mid-scan via `/lights/brightness` or `/lights/toggle`.
  8. Powers on the illumination if not already on.
  9. Executes a **thermal stabilization loop** (`wait_for_light_stable()`) that monitors the optical drift of libcamera's auto-exposure metrics (`ExposureTime * AnalogueGain`). It waits for the LED strips to thermally plateau so exposure levels don't drift mid-scan.
  10. **Re-calls `dual_cameras.prepare_scan(**kwargs, keep_running=True, lock_auto=True)`**: Because `picam2.started` is already `True`, stream reconfiguration is bypassed. The cameras settle auto-exposure and auto-white-balance on the fully warmed-up object and the driver locks them (and copies the values to camera 2). `lock_auto` is passed only in this call, and only to drivers that accept it (`DualCameraRPISync`); a driver that rejects the keyword falls back to an unlocked recalibration with a warning.
  11. Transitions state:
     ```python
     with self._lock:
         if self.state != ScannerState.CANCELLED:
             self.state = ScannerState.PREPARED   # phase = "prepared"
     ```
  A failure ends in `ERROR` with `phase = "error"` and `error = <message>`.

## 🔄 Mechanical Scan Loop (`scan`)

Triggered by `POST /scanner/start`, this method handles the physical 3D capture:

1. **State Lock & Upload Thread**:
   - Transitions state to `RUNNING` (`phase = "scanning"`, status data of the previous run reset).
   - Wipes the local photo directory (`fc.create_clean_dir`, error-checked: a failure or leftovers is a `ScannerError`), creates an empty `manifest.json` and starts the upload worker. The bucket was wiped in `finish_preparation`.
2. **Multi-Level Elevation Loop**:
   - Calculates step count for `z_move_mm` via `distance_to_step_conversion()`.
   - Loops while `not self.up_endstop.is_active` and `not self._cancel_event.is_set()`:
     - Starts a new ring (the ToF verdict of the ring is collected stop by stop, see "ToF policy").
     - **Power Optimization**: Turntable is energized; Z-Axis is disabled (lead screw friction holds height). Z is energized **only while it moves** (explicit `enable()` before each move, `disable()` after it); there is deliberately no "hold torque between rings" option.
     - **360° Rotational Ring**:
       - Calculates steps per jump (`angle_to_steps_conversion(angle)`) and shots per ring as `angle_to_steps(360, TURNTABLE_STEP_TYPE) // steps` (3200 // steps at 1/16), so 22.5 deg gives 16 shots and an angle that does not divide the turn is never rounded up to more than 360 deg.
       - Captures stereoscopic photo pair (`capture_photo()`; a driver `CaptureError` becomes a `ScannerError`).
       - **Verifies both files exist and are non-empty** (`ScannerError` otherwise), appends them to the manifest (written atomically) and only then enqueues them for upload (`_register_photos`).
       - Increments `self.total_photos += len(photo_paths)`.
       - Rotates turntable by `angle` inside `motion_guard()` (using a 20% constant-acceleration speed ramp by default to prevent heavy object slippage, ending in a slow tail of `turntable_end_delay` = `15 ms` per step so the platter has almost no kinetic energy left when it stops).
       - **ToF Verification**: After the rotation, calls `tof.probe_object(threshold)` (until the object has been seen on this ring). See "ToF policy" below and [TOF.md](TOF.md).
       - Pauses for motor vibration settling: the ToF read counts towards it and the loop sleeps whatever remains of `TURNTABLE_SETTLE_S` (`0.2s`), so every stop settles for at least 0.2 s.
     - **Roof Termination Check**: only a ring whose valid readings all showed the backdrop ends the scan early (see "ToF policy"); an unknown ring climbs on.
     - **Elevation Step & Coil Settling Protection**:
       - `time.sleep(0.5)` — Turntable mechanical settling hold (interruptible by cancel).
       - `turntable_motor.disable()` — Cut turntable coil current.
       - `z_axis_motor.enable()` — Energize Z-axis elevator.
       - Climbs UP by `z_move_mm` (`move_z_up()`).
       - `time.sleep(0.5)` — Z-axis elevation settling delay.
       - `z_axis_motor.disable()` — Release Z-axis holding torque.
       - `turntable_motor.enable()` — Re-energize turntable for next horizontal slice.
3. **Zero-photo check**: if the loop ended (not cancelled) with `total_photos == 0` (for example the top endstop was already active at the start) `scan()` raises `ScannerError` instead of reporting success. The number of manifest photos must equal `total_photos`.
4. **Physical end (normal end only)**: motors are released, lights switched off and cameras closed right away (`_teardown_hardware()`), so nothing stays powered for the upload. The state **stays `RUNNING`** (no `IDLE` window) through the next two steps.
5. **Drain** (`phase = "uploading"`): waits until every queued photo is uploaded or failed permanently (see "Upload pipeline"). A cancel aborts it promptly.
6. **Verification** (`phase = "verifying"`): `r2.verify_keys(expected_keys)` lists the bucket and returns the sorted missing keys; this list is authoritative. Then `uploaded_keys`, `missing` (first 50 in the attribute, all of them in the manifest) and `upload_verified = (not missing)` are set, the manifest is finalised and published as `rig/_manifest.json` (best effort, outside the photo set).
   - Nothing missing: the state becomes `finish_state`, `phase = "done"`, `scan()` returns.
   - Anything missing (or the bucket could not be listed): `ScannerUploadError` (a `ScannerError` with `.missing`), state `ERROR`, `phase = "error"`. The local files and `manifest.json` stay untouched.
7. **A failed scan** (exception) publishes `ERROR`, runs `cleanup()` and stops the worker **without** waiting for the backlog (the photos stay on disk). A cancelled scan ends in `CANCELLED` / `phase = "cancelled"` and returns normally.

## ☁️ Upload pipeline (retry, parking, drain, verification)

Slow Wi-Fi or transient socket errors must neither stall the scanner nor lose images. The guarantee that no photo is lost does not come from "retry forever" but from three things: the photos stay on disk until confirmed, the manifest lists everything expected, and the bucket is listed at the end.

| Constant (env override) | Default | Meaning |
|---|---|---|
| `UPLOAD_BACKOFF_S` (`SCAN_UPLOAD_BACKOFF_S`, comma list) | `2, 5, 10, 20, 30` then 30 | Pause before the next attempt of a file (+-`UPLOAD_BACKOFF_JITTER`, default 20 %) |
| `UPLOAD_ATTEMPTS_PER_FILE` (`SCAN_UPLOAD_ATTEMPTS_PER_FILE`) | `8` | Failed attempts after which a file is **parked** |
| `UPLOAD_PARK_RETRY_S` (`SCAN_UPLOAD_PARK_RETRY_S`) | `60` | A parked file gets one attempt per interval |
| `UPLOAD_DRAIN_TIMEOUT_S` (`SCAN_UPLOAD_DRAIN_TIMEOUT_S`) | `1800` | Drain deadline, restarted by every successful upload |
| `MIN_FREE_DISK_MB` (`SCAN_MIN_FREE_DISK_MB`) | `2048` | Preflight disk space |

1. **One worker, no head-of-line blocking**: a file that fails waits for its backoff *without* holding the files behind it. After 8 failed attempts it is parked (not dropped) and retried every 60 s; a later success clears it. A missing or 0-byte file fails immediately and permanently (no retry). Each attempt is `r2.upload_file(path, object_name=key)` (never raises, `False` on failure).
2. **Bookkeeping**: `_pending` (still owed), `_uploaded`, `_upload_failed` (a `set` of failed or parked paths; the boolean view is the `upload_failed` property). A worker of an older scan cannot touch the new scan's sets (generation counter).
3. **Cloud key**: `_cloud_key(path)` = `"rig/" + path relative to input_images` (e.g. `rig/0/lvl_1_shot_0.jpg`), the layout the download code expects.
4. **Drain deadline**: starts when the physical scan ends and restarts at every successful upload, so a slow but progressing uplink is never cut off while a dead one ends after 30 minutes. It replaces the former 45 s stall watchdog.
5. **Verification** is authoritative (`r2.verify_keys`); the counters never decide on their own.

### Manifest (`input_images/manifest.json`)
Written atomically (temp file + `os.replace`) after every photo pair and again after verification:
```json
{"scan_id": "20260101T120000-ab12cd", "started_at": "2026-01-01T12:00:00+00:00",
 "expected_keys": ["rig/0/lvl_1_shot_0.jpg", "..."],
 "photos": [{"key": "...", "path": "...", "size": 4123456, "level": 1, "shot": 0, "camera": 0,
             "exposure_time": 10000, "analogue_gain": 1.5, "colour_gains": [1.8, 1.6], "sensor_timestamp": 123}],
 "uploaded": ["..."], "missing": [], "complete": true}
```
Exposure fields come from the camera driver's `last_capture_info` (null when unavailable). `complete` is true only after a successful verification.

### ToF policy
Per stop, `tof.probe_object(threshold)` (threshold = `TOF_BACKGROUND_DISTANCE_MM - TOF_CLEARANCE_MARGIN_MM`) answers `True` (object), `False` (backdrop seen with valid readings) or `None` (no valid reading). Ring verdict:

| Stops of the ring | Verdict | Effect |
|---|---|---|
| any `True` | object seen | continue climbing |
| at least one `False`, none `True` | cleared | scan ends early (object finished) |
| all `None` | unknown | warning logged and appended to `tof_warnings`; **keeps climbing** (the top endstop bounds it) |

An invalid reading never ends a scan. At the very first ring both "cleared" and "unknown" are reported in `phase_message`.

### Status data (read by the router with `getattr`)
`phase` in `idle / preparing / prepared / scanning / uploading / verifying / done / error / cancelled`, `phase_message`, `level`, `photos_captured` (= `total_photos`), `photos_uploaded`, `missing` (first 50), `uploaded_keys`, `upload_verified`, `error`, `tof_warnings`. They are reset when a new prepare starts and updated at every transition including failures and cancel.

## 🛑 Emergency Stop & Safety

### `emergency_stop()`
Can be called at any time from any thread, never raises, and always ends with `state == CANCELLED`:
1. Under `_lock`: publishes `CANCELLED` **first**, raises `_stopping` and sets `_cancel_event` (also under `_z_stop_lock`, so a Z move either sees the cancel in `_begin_z_motion()` or is already flagged as moving when the STOP goes out).
2. Sends `stop(repeat=2)` to **both** motors back to back (the universal `0xFF` twice; no `DISABLE`, which blocks until the running move has ended, sits between them).
3. Only then releases the torque (`disable(settle_delay=0)` on both motors).
4. Turns OFF relay lights and unlocks the brightness.
5. Closes active camera streams and releases hardware video locks.
6. Sends a final STOP to both motors (catches a move a straggler thread started meanwhile).
7. `finally`: clears `_stopping` (depth-counted, so overlapping stops do not clear it early) and re-asserts `CANCELLED`.

Every step is in its own `try/except` with logging: a failing first motor does not prevent the second motor, the lights, the cameras or the state change.

### Cancel semantics for moves
* `_cancel_event` stays set after an emergency stop until the next `setup_and_stream()`/`scan()` clears it.
* `move_z_up`/`move_z_down` re-check it under `_z_stop_lock` right before flagging the move (`_begin_z_motion()` returns `False`) and return `False` without sending anything. `home_z_axis()`/`move_z_to_top()` raise `ScannerError` before their first command, and `finish_preparation()` returns before homing.
* The check is applied for the prepare/scan threads (they mark themselves) and for any caller while the state is `PREPARING`/`PREPARED`/`RUNNING`. A **stale** flag (state `IDLE`/`CANCELLED`, called from a `/test` endpoint) does **not** block manual moves.

### `cleanup()`
Called during normal teardown or error recovery (the hardware part is `_teardown_hardware()`, which a successful scan calls on its own so the state can stay `RUNNING` during the drain). Each step is exception-safe (a failing motor does not leave the lights on or the cameras open):
* Cuts torque to stepper motor coils so they do not overheat while standing still.
* Powers off lights.
* Stops camera streams.
* Does **not** overwrite terminal states (`CANCELLED`, `ERROR`, `COMPLETED`), and does not touch the state at all while `_stopping` is set.

## 📚 Class Method Reference

### Constructor & Properties

#### `Scanner(xvs: Optional[bool] = None, camera_mode: Optional[str] = None)`
Initializes motion controllers, safety limit interrupts, LED illumination, and camera mode configuration.
- **`camera_mode` Resolution Hierarchy**:
  1. Explicit `camera_mode` argument (`"rpi_sync"`, `"xvs"`, or `"staggered"`).
  2. Legacy `xvs` boolean flag: `xvs=True` maps to `"xvs"`, `xvs=False` falls back to `CAMERA_MODE` env var.
  3. Environment variable `CAMERA_MODE` (case-insensitive).
  4. Default production fallback: `"rpi_sync"`.

#### `is_streaming -> bool`
Dynamic property returning `True` if `self.dual_cameras` is initialized and actively capturing live frames.

#### `level -> int`
Returns the current elevation slice count during an active 3D scan sequence.

#### `preflight() -> None`
Cloud, ToF and disk checks (see Phase 1). Raises `ScannerPreflightError`. Called by `setup_and_stream()` before the state transition.

#### `ScannerUploadError(ScannerError)`
Raised by `scan()` when photos are missing from the bucket after the drain; `.missing` is the sorted list of cloud keys.

### Lifecycle & Motion

#### `setup_and_stream(enable_stream: bool = True, bitrate: int = 4_000_000, camera_mode: Optional[str] = None, **kwargs) -> list[str] | None`
Runs the preflight, closes stale cameras, starts camera sensors using the resolved camera driver (`DualCameraRPISync`, `DualCameraXVS`, or `DualCamera`), boots the stream and returns stream URLs (`None` when a cancel landed meanwhile).

#### `finish_preparation(**kwargs) -> None`
Background worker for homing down, +30mm offset, R2 bucket cleanup, thermal stabilization, and in-place camera calibration (with `lock_auto=True`).

#### `motion_guard() -> ContextManager`
Non-blocking, re-entrant (per thread) exclusive right to move the rig. Raises `ScannerBusyError` immediately when another thread holds it. Used by `move_z_up`/`move_z_down`, `home_z_axis`, `move_z_to_top` and the turntable rotation of a ring; external callers (the `/test` router) wrap their own moves in it.

#### Module constants
`Z_TRAVEL_MAX_MM = 150` (Z axis travel, from the specification) and `Z_HOMING_MARGIN_MM = 15`: homing and move-to-top are limited to their sum, 165 mm = **16500 steps** at 1/4 microstepping (100 steps/mm), instead of the former 50000.

#### `home_z_axis(delay: float = 0.0015, start_delay: float = 0.004, ramp_percent: float = 0.1, acceleration: bool = True) -> None`
Drives carriage downward in acceleration-controlled pulses until `down_endstop` triggers, for at most 16500 steps. The coils are released right away after the endstop STOP (the STOP already disabled the driver, so there is no extra settling pause on that path). With `acceleration=False` the move runs at the constant `delay` (`start_delay` / `ramp_percent` ignored). Raises `ScannerError` when the endstop was not reached (aborted or cancelled move, or the travel budget ran out) and `ScannerBusyError` if another motion is in progress; motor/serial errors are propagated, not swallowed.

#### `move_z_to_top(delay: float = 0.0015, start_delay: float = 0.004, ramp_percent: float = 0.1, acceleration: bool = True) -> None`
Drives carriage upward until `up_endstop` triggers (same 16500-step budget), after which the coils are released (no extra settling pause on this path: the endstop STOP already disabled the driver). Raises `ScannerError` when the endstop was not reached.

#### `move_z_up_distance(distance: float = 100.0, delay: float = 0.002, ...) -> bool`
Moves carriage UP by distance in millimeters. Blocked if top limit switch is active; `ScannerBusyError` if another motion is in progress; returns `False` (nothing sent) when a cancel applies.

#### `move_z_down_distance(distance: float = 100.0, delay: float = 0.002, ...) -> bool`
Moves carriage DOWN by distance in millimeters. Blocked if bottom limit switch is active; same busy/cancel behaviour as the UP variant.

#### `scan(angle: float = 18.0, delay_turntable: float = 0.0010, z_move_mm: float = 100.0, delay_z_motor: float = 0.0010, turntable_acceleration: bool = True, ..., turntable_end_delay: float | None = 0.015, z_end_delay: float | None = None, finish_state: str = "idle") -> None`
Executes full physical scanning and parallel image upload sequence with independent acceleration profiles and 0.5s motor power settling delays during level transitions, then drains and verifies the upload (see "Mechanical Scan Loop" steps 4-7). Raises `ScannerUploadError` when photos are missing.
* `turntable_end_delay`: step delay (s) at the end of each turntable deceleration (slow stop), clamped to `[0.005, 0.030]`; `None` disables it. Default `0.015`.
* `z_end_delay`: same for the Z-axis; `None` (default) disables it.
* `finish_state`: state left after a scan that completed normally **and was verified** (default `idle`). The state stays `RUNNING` until the drain and verification are done, then goes straight to `finish_state`: the API passes `processing`, so there is no `idle` gap in which a new `/scanner/prepare` could be accepted before the cloud pipeline starts. The end-delay tail is dropped automatically when the matching `*_acceleration` is `false`.
* After the `+30 mm` start-position move in `finish_preparation()` the Z driver is released (the lead screw holds the carriage), so it is not energized at 1.8 A while waiting for `/scanner/start`.
* A climb that ends exactly on the top switch now takes the final top ring; a cancel that tears the hardware down under the scan thread ends the scan quietly instead of raising.
* `move_z_up()` / `move_z_down()` and the `move_z_*_distance()` helpers accept `end_delay` as well (default `None`).

#### `generate_livestream(bitrate: int = 4_000_000) -> list[str] | None`
Generates RTSP stream endpoints using the active camera driver.

#### `stop_stream() -> None`
Terminates RTSP/MJPEG streams and releases camera hardware locks.

#### `emergency_stop() -> None`
Immediately halts all motion via Arduino `0xFF` abort (sent twice to both motors before any `DISABLE`), cuts coil power, kills lights, closes the cameras and publishes `CANCELLED` (see above). Exception-safe.

#### `cleanup() -> None`
Safe power down of motors and lights without clearing terminal states.

#### `close_hardware() -> None`
Explicitly releases GPIO limits, I2C buses, and calls `bridge.close()` to fire a final `0xFF` emergency stop to the Arduino before releasing the OS serial port.
