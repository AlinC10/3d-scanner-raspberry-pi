# Scanner Hardware Controller (`../scanner.py`)

The `Scanner` class in `../scanner.py` is the central hardware abstraction layer and real-time physical orchestrator of the 3D scanner rig. 

It manages the lifecycle of the stepper motors, safety limit switches, high-power illumination LEDs, stereoscopic camera feeds, and background cloud uploads. It is engineered specifically for thread-safe, non-blocking operation inside multi-threaded asynchronous servers (such as FastAPI).

---

## 🏗️ Architectural Pillars

```
                     ┌───────────────────────────────────────────────┐
                     │          Scanner Singleton Instance           │
                     └───────┬──────────────┬──────────────┬─────────┘
                             │              │              │
                ┌────────────┴───┐   ┌──────┴─────┐  ┌─────┴─────────────────────┐
                │ Stepper Motors │   │ Endstops   │  │ BaseDualCamera Hierarchy  │
                │ Turntable/Z    │   │ Up / Down  │  │ DualCameraRPISync (rpi.sync)│
                └────────────────┘   └────────────┘  │ DualCameraXVS (xvs)       │
                                                     │ DualCamera (staggered)    │
                                                     └─────────────┬─────────────┘
                                                                   │
                                                     ┌─────────────┴─────────────┐
                                                     │ Parallel Upload Pipeline  │
                                                     │ Queue + Drain -> R2       │
                                                     └───────────────────────────┘
```

1. **Non-Blocking Lock Scoping**: Mutex locks (`self._lock`) are acquired *only* for state validation and microsecond-level state transitions. Long-running mechanical loops run strictly **outside** the lock, ensuring API requests like `/status` and `/cancel` are processed with zero latency.
2. **Cooperative Thread Cancellation**: Instead of forcefully terminating Python threads, a `threading.Event()` (`self._cancel_event`) is checked at every critical hardware boundary (before each rotational stop, photo trigger, and Z-axis lift).
3. **Producer-Consumer Background Uploads**: Capturing images and uploading to Cloudflare R2 are decoupled through an asynchronous worker queue (per-file retry with backoff, parking of failing files, a progress-based drain deadline and a final bucket verification against a manifest; see "Upload pipeline" below). The capture thread never waits for an upload.
4. **Hardware Safety Interrupts**: Both limit switches are wired to `motor.stop()`, but only act while a Z move is in flight (`_z_moving` flag set by `move_z_up`/`move_z_down`); a press while Z is idle is ignored, because the `0xFF` stop is universal and would abort the turntable or cut every motor. Because motor steps are generated by the Arduino, calling `stop()` instantly injects the out-of-band `0xFF` universal abort byte over UART, halting the hardware stepping loop in $\le 1.0\text{ ms}$ without waiting for Python interpreter cycles.
5. **Exclusive Motion (`motion_guard()`)**: Every physical move (`move_z_up`/`move_z_down` and everything built on them, `home_z_axis`, `move_z_to_top`, the turntable rotation of a ring, and the `/test` moves) runs inside `with scanner.motion_guard():`. The guard is **non-blocking**: if another thread already holds it, it raises `ScannerBusyError` (a `ScannerError`; the `/test` router maps it to `409`) and nothing is sent to the Arduino. It is re-entrant for the owning thread, so the helpers nest freely inside one `scan()`. Without it two overlapping Z moves would share the `_z_moving` flag and the single STOP budget, and the first one to end would silently remove the endstop protection of the other.
7. **Direction-aware endstops**: `_z_direction` ("up" / "down") is set by `move_z_up` / `move_z_down` before the move is flagged and cleared when it ends. An endstop edge only stops a move travelling *towards* that switch; a late or bouncing edge of the switch the carriage is leaving is ignored (it used to abort the +30 mm climb right after homing). The level watchdog already watched only the switch in the direction of travel.
8. **Mechanical Settling Hold**: Stepper coil de-energization (`disable()`) is preceded by a 0.5-second pause (`settle_delay`, interruptible by a cancel) during which the coils keep holding the rotor. Cutting the current while the platter or carriage still carries kinetic energy lets it coast past the target. (An electrical benefit, i.e. avoiding back-EMF transients on the shared 12 V bus that were suspected of resetting the Arduino, is an unverified hypothesis; the Arduino now recovers from a reset by itself.)
9. **Constant speed on Z**: the Z helpers (`move_z_up`/`move_z_down` and everything built on them) and `Motor.rotate_distance` default to `acceleration=False`; the Z axis is ramped only when a caller asks for it explicitly (`StartRequest.mechanical.z_axis.acceleration`, the `/test` moves). The turntable helpers keep the ramp by default.
10. **Runs without the Arduino**: a missing Arduino no longer stops the server (API-21). `Motor()` keeps the configuration error (`configured`, `config_error`) instead of raising, and every request that moves a motor first calls `require_motors()` (see below), which reconnects and raises `ArduinoUnavailableError` (HTTP 503) when the Arduino does not answer.

## 🚦 State Machine (`ScannerState`)

The scanner enforces strict lifecycle state transitions:

```
  IDLE / COMPLETED / CANCELLED / ERROR
    │  POST /scanner/prepare (mode "object")      │  POST /scanner/face/prepare (mode "face")
    ▼                                             ▼
  PREPARING ──► PREPARED ──► RUNNING (object scan, POST /scanner/start: needs mode "object")
                    │           │
                    │           ├──► COMPLETED (photos verified in R2; cloud.launch_runpod = false, the default)
                    │           └──► PROCESSING ──► DOWNLOADING ──► COMPLETED   (only with cloud.launch_runpod = true)
                    └──────► RUNNING (face scan, POST /scanner/face/capture: needs mode "face") ──► COMPLETED (face_result)

  Any of PREPARING / PREPARED / RUNNING / PROCESSING / DOWNLOADING ──► CANCELLED (POST /scanner/cancel)
                                                                  └──► ERROR (hardware, upload verification, cloud)
```

* **`mode`** (`ScanMode`: `"object"`, `"face"`, or `None` for a manual `/test` session or before any prepare) says what the last prepare readied the rig for; it is set by `setup_and_stream(scan_mode=...)` and shown by `GET /scanner/status`. `scan()` refuses a face prepare and `begin_face_scan()` an object prepare (`ScannerModeError`, 400). It stays set after the run.
* **`z_position_mm`**: carriage height above the bottom endstop, known after a prepare homed it (`finish_preparation` sets it to the start height); the face moves keep it up to date; `None` after a cancel, an aborted move or an endstop stop.
* **`PREPARE_ALLOWED = ("idle", "completed", "cancelled", "error")`**: Allows re-preparing after a finished or aborted run without requiring an application restart.
* **`TERMINAL = ("completed", "cancelled", "error")`**: Preserved by `cleanup()` so API consumers and frontend polling loops can read the final run outcome without having it prematurely overwritten back to `IDLE`.
* **`_stopping` flag**: Raised by `emergency_stop()` (after it has published `CANCELLED`, under `_lock`) and cleared in its `finally`. While it is set, `setup_and_stream()` refuses a new `/prepare` with `ScannerStoppingError` (a `RuntimeError`, `conflict = True`; the router answers **409**) and `cleanup()` does not touch the state. This is a *mitigation*: a new prepare can no longer clear `_cancel_event` while the old run is still winding down. It is not a per-run token: old threads still share `_cancel_event` and the hardware (a `run_id` per run is the full fix, see `../../plans/implemented/MOTOR_FIXES_PLAN.md` section 7).

## 🎬 Two-Phase Preparation Architecture

To deliver an immediate live video feed to the frontend while accommodating 15–40 seconds of physical carriage travel, preparation is divided into two distinct phases:

### Phase 1: Immediate Stream Startup (`setup_and_stream`)
* **Execution**: Synchronous (duration: ~1.5s).
* **Actions**:
  0. **Arduino** (`require_motors()`, before any state change, only for a scan prepare): the Arduino must answer a PING (the bridge reconnects first) and both motors must be configured on it, otherwise `ArduinoUnavailableError` (503) and nothing is touched.
     **Preflight** (`preflight()`, before any state change): `r2.preflight()` (credentials, write/read/delete rights), the ToF sensor (`require_tof()`: available and a valid test reading; a sensor that fails is reinitialised once with `ToFSensor.reinitialize()` before the refusal, PERI-10), and at least `MIN_FREE_DISK_MB` (2048) free under `input_images/`. The first failure raises `ScannerPreflightError` (a `RuntimeError`, so the router answers 400 with the message); the state stays `IDLE` and `phase = "error"`, `error = <message>`. `SCAN_PREFLIGHT=0` skips the checks (development only).
  1. Validates state in `PREPARE_ALLOWED` and transitions to `PREPARING`.
  1b. Closes any stale `dual_cameras` (`_close_cameras()`) and calls `lights.unlock_brightness()`, so a second prepare in the same process never meets "device busy" or a frozen dimmer.
  1c. Refuses a brightness of 0 (`ScannerError`) **before** the lights go on.
  2. Powers ON chamber lights (`_lights_on_unless_cancelled()`: switched on under `_lock` only if no cancel is pending, so a stop can never be followed by the lights coming back on, SCAN-11).
  3. **Resolves Camera Driver Mode**: Dynamically selects camera implementation based on resolution hierarchy:
     $$\text{call-level } \mathtt{camera\_mode} \longrightarrow \mathtt{kwargs["camera\_mode"]} \longrightarrow \mathtt{self.camera\_mode} \longrightarrow \text{Default: } \mathtt{"rpi\_sync"}$$
     - `"rpi_sync"` / `"sync"`: Instantiates `DualCameraRPISync` (continuous libcamera `rpi.sync`, DMA triple-buffering, spectator-driven on-demand MJPEG encoding).
     - `"xvs"`: Instantiates `DualCameraXVS` (hardware pin Master/Slave frame sync with asymmetric startup).
     - `"staggered"`: Instantiates `DualCamera` (software multi-threading with 0.15s dispatch stagger).
  4. Calls `dual_cameras.prepare_scan(..., keep_running=True)` to initialize the sensor pipeline (AE/AWB are **not** locked yet). The cancel flag is re-checked after the camera construction, after `prepare_scan` and after the stream start: a cancel that landed meanwhile closes the new cameras, switches the lights off and returns `None`.
  5. Boots live streaming:
     - Starts the MJPEG preview via `generate_livestream()` and stores the URLs in `self.stream_urls`. Its size is `preview_resolution` (passed to the sync driver as `stream_size`).
     - Powers native browser-friendly MJPEG streaming via `/scanner/stream/mjpeg` with zero idle CPU overhead.
  6. **Returns `stream_urls` immediately** to the caller.

### Phase 2: Asynchronous Homing & Auto-Tuning (`finish_preparation`)
* **Execution**: Asynchronous background task (via `FastAPI.BackgroundTasks`).
* **Actions**:
  1. Safely strips out initialization kwargs (`master_id`, `slave_id`, `video_resolution`, `rotation`) to prevent downstream signature errors.
  2. Checks for cancellation (`_cancel_event`) **before the first command**, then moves the carriage down to the bottom endstop (`home_z_axis()`, at most `Z_TRAVEL_MAX_MM + Z_HOMING_MARGIN_MM` = 475 + 15 = 490 mm = 49000 steps). Incorporates a **0.5-second settling pause** before de-energizing the Z-axis coil (`disable()`); the pause is a mechanical settle, not a verified electrical protection.
  3. Checks for cancellation: `if self._cancel_event.is_set(): return`. Then waits `Z_HOME_SETTLE_S` (1 s, env `SCAN_Z_HOME_SETTLE_S`) with the carriage on the bottom endstop before the climb; a cancel ends the wait at once.
  4. Energizes Z explicitly (`z_axis_motor.enable()`, no reliance on the firmware's auto-enable) and raises the carriage by `z_start_mm` (`PrepareRequest.z_start_mm`, default **30.0 mm**, 0 to 100) to rest directly in front of the illuminated object, then releases the driver again. `0` skips the climb (the carriage stays on the bottom endstop). The value must convert to a whole number of Z steps (`distance_to_step_conversion`, checked before the homing starts; the request schema validates it too).
  5. Re-checks that the brightness is not 0 (the user may have changed it), then deletes the R2 job folders `jobs/<id>/` untouched for longer than `SCAN_R2_STALE_JOB_S` (24 h, `r2.delete_stale_jobs`), best effort: a failure is only a warning, because every scan uploads under its own prefix and nothing of an older scan can be mixed in. The bucket is no longer wiped. (The local photo directory is wiped at the start of `scan()`.)
  6. **Locks the brightness API** (`self.lights.lock_brightness()`) so operators cannot accidentally dim the lights mid-scan via `/lights/brightness` or `/lights/toggle`.
  7. Powers on the illumination if not already on (through `_lights_on_unless_cancelled()`: a cancel that arrived meanwhile ends the preparation with the lights off).
  8. Executes a **thermal stabilization loop** (`wait_for_light_stable()`) that monitors the optical drift of libcamera's auto-exposure metrics (`ExposureTime * AnalogueGain`). It waits for the LED strips to thermally plateau so exposure levels don't drift mid-scan. The drift is measured on camera 1 only (the two cameras see the same light).
  9. **Re-calls `dual_cameras.prepare_scan(**kwargs, keep_running=True, lock_auto=True, copy_colour_gains=...)`**: Because `picam2.started` is already `True`, stream reconfiguration is bypassed. With `focus="auto"` the sync driver first runs its autofocus sweep here (in front of the lit object) and leaves each lens on its sharpest position; then the cameras settle auto-exposure and auto-white-balance on the fully warmed-up object and the driver locks them. Exposure time and analogue gain of camera 1 are copied to camera 2; the white-balance gains only with `copy_colour_gains=true` (default `false`: each camera keeps the gains its own AWB settled on, because the same gains give camera 2 a colour cast). `lock_auto` is passed only in this call, and only to drivers that accept it (`DualCameraRPISync`); a driver that rejects the keyword falls back to an unlocked recalibration with a warning.
  10. Transitions state:
     ```python
     with self._lock:
         if self.state != ScannerState.CANCELLED:
             self.state = ScannerState.PREPARED   # phase = "prepared"
     ```
  A failure ends in `ERROR` with `phase = "error"` and `error = <message>`.

## 🔄 Mechanical Scan Loop (`scan`)

Triggered by `POST /scanner/start`, this method handles the physical 3D capture:

1. **State Lock & Upload Thread**:
   - Transitions state to `RUNNING` (`phase = "scanning"`, status data of the previous run reset).
   - Wipes the local photo directory (`fc.create_clean_dir`, error-checked: a failure or leftovers is a `ScannerError`), gives the photo set its `job_id` (`StartRequest.job_id` or `r2.new_job_id()`, in `/status`), creates an empty `manifest.json` (`scan_id` = `job_id`) and starts the upload worker.
2. **Multi-Level Elevation Loop**:
   - Calculates step count for `z_move_mm` via `distance_to_step_conversion()`.
   - Loops while `not self.up_endstop.is_active` and `not self._cancel_event.is_set()`:
     - Starts a new ring (the ToF verdict of the ring is collected stop by stop, see "ToF policy").
     - **Power**: the turntable is energized at the start of the scan and **stays energized until the scan ends**, also during the Z climbs (M9: a released platter could be nudged and the next ring would start at another angle). Z is energized **only while it moves** (explicit `enable()` before each move, `disable()` after it): the lead screw friction holds the height between rings; there is deliberately no "hold Z torque between rings" option.
     - **360° Rotational Ring**:
       - Calculates steps per jump (`angle_to_steps_conversion(angle)`) and shots per ring as `angle_to_steps(360, TURNTABLE_STEP_TYPE) // steps` (3200 // steps at 1/16), so 22.5 deg gives 16 shots and an angle that does not divide the turn is never rounded up to more than 360 deg.
       - Captures stereoscopic photo pair (`capture_photo()`; a driver `CaptureError` becomes a `ScannerError`).
       - **Verifies both files exist and are non-empty** (`ScannerError` otherwise), appends them to the manifest (written atomically) and only then enqueues them for upload (`_register_photos`).
       - The **first pair of the scan** must not be black (mean luma below `BLACK_FRAME_MEAN_MAX` on a 1/8-size read): a closed lens cap, dead lights or a manual exposure of 0 end the scan at once with a `ScannerError` that names the camera and the reported exposure, instead of after 160 black photos. `SCAN_BLACK_FRAME_CHECK=0` turns the check off; without OpenCV the photo cannot be judged and passes.
       - Increments `self.total_photos += len(photo_paths)`.
       - Rotates turntable by `angle` inside `motion_guard()` (using a 20% constant-acceleration speed ramp by default to prevent heavy object slippage, ending in a slow tail of `turntable_end_delay` = `15 ms` per step so the platter has almost no kinetic energy left when it stops).
       - **ToF Verification**: After the rotation, calls `tof.probe_object(threshold)` (until the object has been seen on this ring). See "ToF policy" below and [TOF.md](TOF.md).
       - Pauses for motor vibration settling: the ToF read counts towards it and the loop sleeps whatever remains of `TURNTABLE_SETTLE_S` (`0.2s`), so every stop settles for at least 0.2 s.
     - **Roof Termination Check**: only a ring whose valid readings all showed the backdrop ends the scan early (see "ToF policy"); an unknown ring climbs on.
     - **Elevation Step** (the cancel flag is checked before every step):
       - `z_axis_motor.enable()` — Energize Z-axis elevator (the turntable keeps its holding torque).
       - Climbs UP by `z_move_mm` (`move_z_up()`).
       - `z_axis_motor.disable(interrupt=_cancel_event)` — 0.5 s Z settling hold (interruptible by a cancel), then release the Z torque.
       - `turntable_motor.enable()` — only re-asserts the turntable's torque (it was never released; this covers an Arduino reset during the climb).
3. **Zero-photo check**: if the loop ended (not cancelled) with `total_photos == 0` (for example the top endstop was already active at the start) `scan()` raises `ScannerError` instead of reporting success. The number of manifest photos must equal `total_photos`.
4. **Physical end (normal end only)**: motors are released, lights switched off and cameras closed right away (`_teardown_hardware()`), so nothing stays powered for the upload. The state **stays `RUNNING`** (no `IDLE` window) through the next two steps.
5. **Drain** (`phase = "uploading"`): waits until every queued photo is uploaded or failed permanently, for at most `UPLOAD_DRAIN_TIMEOUT_S` (5 min) without a single successful upload (see "Upload pipeline"). A cancel aborts it promptly.
6. **Verification** (`phase = "verifying"`): `r2.verify_keys(expected_keys)` lists the bucket and returns the sorted missing keys; this list is authoritative. Then `uploaded_keys`, `missing` (first 50 in the attribute, all of them in the manifest) and `upload_verified = (not missing)` are set, the manifest is finalised and published as `rig/_manifest.json` (best effort, outside the photo set).
   - Nothing missing: the state becomes `finish_state`, `phase = "done"`, `scan()` returns.
   - Anything missing (or the bucket could not be listed): `ScannerUploadError` (a `ScannerError` with `.missing`), state `ERROR`, `phase = "error"`. The local files and `manifest.json` stay untouched.
7. **A failed scan** (exception) publishes `ERROR`, runs `cleanup()` and stops the worker **without** waiting for the backlog (the photos stay on disk). A cancelled scan ends in `CANCELLED` / `phase = "cancelled"` and returns normally.

## ☁️ Upload pipeline (retry, parking, drain, verification)

Slow Wi-Fi or transient socket errors must neither stall the scanner nor lose images. The guarantee that no photo is lost does not come from "retry forever" but from three things: the photos stay on disk until confirmed, the manifest lists everything expected, and the bucket is listed at the end.

| Constant (env override) | Default | Meaning |
|---|---|---|
| `UPLOAD_BACKOFF_S` (`SCAN_UPLOAD_BACKOFF_S`, comma list) | `2, 5, 10, 20, 30` then 30 | Pause before the next attempt of a file (+-`UPLOAD_BACKOFF_JITTER`, default 20 %) |
| `UPLOAD_ATTEMPTS_PER_FILE` (`SCAN_UPLOAD_ATTEMPTS_PER_FILE`) | `8` | Failed attempts after which a file is **parked** |
| `UPLOAD_PARK_RETRY_S` (`SCAN_UPLOAD_PARK_RETRY_S`) | `60` | A parked file gets one attempt per interval |
| `UPLOAD_DRAIN_TIMEOUT_S` (`SCAN_UPLOAD_DRAIN_TIMEOUT_S`) | `300` | Drain deadline, restarted by every successful upload (5 min: past that without one success, something is wrong with the uplink) |
| `cloud.cloudflare_r2.UPLOAD_ATTEMPT_TIMEOUT_S` (`SCAN_UPLOAD_ATTEMPT_TIMEOUT_S`) | `300` | Total time of **one** upload attempt of one file; checked on every chunk sent (boto3 progress callback), the attempt then fails and the file goes to its backoff. A connection that sends nothing at all ends earlier, at the 60 s socket `read_timeout` |
| `UPLOAD_BACKOFF_JITTER` (`SCAN_UPLOAD_BACKOFF_JITTER`) | `0.2` | Random spread of the backoff |
| `MIN_FREE_DISK_MB` (`SCAN_MIN_FREE_DISK_MB`) | `2048` | Preflight disk space |
| `CAPTURE_ATTEMPTS` (`SCAN_CAPTURE_ATTEMPTS`) | `3` | Attempts to take one photo pair |
| `BLACK_FRAME_MEAN_MAX` (`SCAN_BLACK_FRAME_MEAN_MAX`, `SCAN_BLACK_FRAME_CHECK=0` disables) | `3.0` | Mean luma (0-255) below which a photo counts as black |
| `Z_HOME_SETTLE_S` (`SCAN_Z_HOME_SETTLE_S`) | `1` | Pause on the bottom endstop after the homing of `finish_preparation` |

1. **One worker, no head-of-line blocking**: a file that fails waits for its backoff *without* holding the files behind it. After 8 failed attempts it is parked (not dropped) and retried every 60 s; a later success clears it. A missing or 0-byte file fails immediately and permanently (no retry). Each attempt is `r2.upload_file(path, object_name=key)` (never raises, `False` on failure), limited to `UPLOAD_ATTEMPT_TIMEOUT_S` (5 min) in total, so one trickling upload cannot hold the single worker for longer.
2. **Bookkeeping**: `_pending` (still owed), `_uploaded`, `_upload_failed` (a `set` of failed or parked paths; the boolean view is the `upload_failed` property). A worker of an older scan cannot touch the new scan's sets (generation counter).
3. **Cloud key**: `_cloud_key(path)` = `r2.input_key(job_id, "rig/" + path relative to the photo root)` (e.g. `jobs/20261030-101500-a1b2c3/input/rig/0/f_1000.jpg`), the layout Turntable Studio reads. The photo root is `input_images/rig/` (`INPUT_IMAGES_DIR`); only that folder is wiped at the start of a scan. The verification lists only `jobs/<job_id>/input/`; the manifest goes to `jobs/<job_id>/_manifest.json`.
4. **Drain deadline**: starts when the physical scan ends and restarts at every successful upload, so a slow but progressing uplink is never cut off while a dead one ends after 5 minutes (it was 30 before 2026-10-28). The photos then stay on disk and the run ends in `error` with `missing`; there is no re-upload from the manifest yet. It replaces the former 45 s stall watchdog.
6. **Progress in `/status`** (`upload_progress()`): `seconds_since_last_upload` (since the last successful upload, or since the worker or the drain started, whichever is later; `null` when no upload worker runs) and `upload_drain_timeout_s` (the drain limit), so a client can show "no progress for 2 min of 5".
5. **Verification** is authoritative (`r2.verify_keys`); the counters never decide on their own.

### Manifest (`input_images/rig/manifest.json`)
Written atomically (temp file + `os.replace`) after every photo pair and again after verification:
```json
{"scan_id": "20260101T120000-ab12cd", "started_at": "2026-01-01T12:00:00+00:00",
 "expected_keys": ["rig/0/f_1000.jpg", "..."],
 "photos": [{"key": "...", "path": "...", "size": 4123456, "level": 1, "shot": 0, "camera": 0,
             "exposure_time": 10000, "analogue_gain": 1.5, "colour_gains": [1.8, 1.6], "sensor_timestamp": 123}],
 "uploaded": ["..."], "missing": [], "complete": true}
```
Exposure fields come from the camera driver's `last_capture_info` (null when unavailable). `complete` is true only after a successful verification.

### Photo pairs are never half (`SCAN_CAPTURE_ATTEMPTS`)
`_capture_turntable_slice` asks `capture_photo` for the pair of the current position. When it raises `CaptureError` (a missing frame, a file not written) the file of the camera that did succeed is deleted (`_discard_partial_pair`) and the pair is retaken at the same position (the turntable has not moved), up to `SCAN_CAPTURE_ATTEMPTS` times in total (default 3). After the last failure the scan stops with `ScannerError("Photo capture failed at level L, shot S (attempt N of N): ...")`. A pair is only registered in the manifest and queued for upload once both files are complete.

### Who owns the rig (`scan_owns_rig`, manual sessions)
`Scanner.scan_owns_rig` is true in the states `preparing`, `prepared` and `running`. The `/test` light and snap endpoints answer `409` then, and `DimmableLight.off(force=False)` (the form used by `/test/lights/disable`) refuses to lift the brightness lock; the scanner's own teardown calls `off()` (forced). A manual session started by `/test/stream/start` or `/test/camera/snap` (`setup_and_stream(preflight=False)`) sets `_manual_session`: it does not own the rig, and `stop_stream()` ends it (cameras released, lights off, state back to `IDLE`) so that `/scanner/prepare` is accepted again.

### ToF policy
Per stop, `tof.probe_object(threshold)` (threshold = `TOF_BACKGROUND_DISTANCE_MM`, 440 mm: a reading below it is the object, there is no extra margin) answers `True` (object), `False` (backdrop seen with valid readings) or `None` (no valid reading). Ring verdict:

| Stops of the ring | Verdict | Effect |
|---|---|---|
| any `True` | object seen | continue climbing |
| at least one `False`, none `True` | cleared | scan ends early (object finished) |
| all `None` | unknown | warning logged and appended to `tof_warnings`; **keeps climbing** (the top endstop bounds it) |

An invalid reading never ends a scan. At the very first ring both "cleared" and "unknown" are reported in `phase_message`.

### Status data (read by the router with `getattr`)
`phase` in `idle / preparing / prepared / scanning / uploading / verifying / done / error / cancelled`, `phase_message`, `cloud_message` (set by the router during a RunPod job: technical detail, apart from the milestones in `phase_message`), `level`, `photos_captured` (= `total_photos`), `photos_uploaded`, `missing` (first 50), `uploaded_keys`, `upload_verified`, `error`, `tof_warnings`, `face_result` (outcome of a completed face scan), and `upload_progress()` (see the upload pipeline). They are reset when a new prepare or face scan starts and updated at every transition including failures and cancel.

## 🛑 Emergency Stop & Safety

### `emergency_stop()`
Can be called at any time from any thread, never raises, and always ends with `state == CANCELLED`:
1. Under `_lock`: publishes `CANCELLED` **first**, raises `_stopping` and sets `_cancel_event` (also under `_z_stop_lock`, so a Z move either sees the cancel in `_begin_z_motion()` or is already flagged as moving when the STOP goes out).
2. Sends `stop(repeat=2)` to **both** motors back to back (the universal `0xFF` twice; no `DISABLE`, which blocks until the running move has ended, sits between them).
3. Only then releases the torque (`disable(settle_delay=0)` on both motors).
4. Turns OFF relay lights and unlocks the brightness.
5. Closes active camera streams and releases hardware video locks.
6. Sends a final STOP to both motors (catches a move a straggler thread started meanwhile) and switches the lights off once more: in `CANCELLED` every peripheral is off (SCAN-11).
7. `finally`: clears `_stopping` (depth-counted, so overlapping stops do not clear it early) and re-asserts `CANCELLED`.

Every step is in its own `try/except` with logging: a failing first motor does not prevent the second motor, the lights, the cameras or the state change.

### Cancel semantics for moves
* `_cancel_event` stays set after an emergency stop until the next `setup_and_stream()`/`scan()` clears it.
* `move_z_up`/`move_z_down` re-check it under `_z_stop_lock` right before flagging the move (`_begin_z_motion()` returns `False`) and return `False` without sending anything. `home_z_axis()`/`move_z_to_top()` raise `ScannerError` before their first command, and `finish_preparation()` returns before homing.
* The check is applied for the prepare/scan threads (they mark themselves) and for any caller while the state is `PREPARING`/`PREPARED`/`RUNNING`. A **stale** flag (state `IDLE`/`CANCELLED`, called from a `/test` endpoint) does **not** block manual moves.

### `cleanup()`
Called during normal teardown or error recovery (the hardware part is `_teardown_hardware()`, which a successful scan calls on its own so the state can stay `RUNNING` during the drain). Each step is exception-safe (a failing motor does not leave the lights on or the cameras open):
* Cuts torque to stepper motor coils so they do not overheat while standing still.
* Powers off lights.
* Stops camera streams.
* Does **not** overwrite terminal states (`CANCELLED`, `ERROR`, `COMPLETED`), and does not touch the state at all while `_stopping` is set.

## 📚 Class Method Reference

### Constructor & Properties

#### Opening the hardware
`Scanner.__init__` opens the ToF sensor, the two motors (and with them the Arduino bridge), the two endstops and the lights, in this order. A missing **Arduino** or **ToF sensor** does not fail the construction: the motors keep their configuration error until `require_motors()` succeeds, the ToF sensor reports `available = False` until `require_tof()` reinitialises it. The lifespan of `main_prod.py` also keeps the server running when the construction fails for another reason (logged; the scanner is built again on the next request that uses it). If one of the other pieces fails (for example the PWM chip when `dtoverlay=pwm-2chan` is missing), `close_hardware()` releases the ones already opened before the error is raised: the GPIO pins, the I2C bus and the serial port do not stay claimed, so a new attempt in the same process (the lazy `_LazyScanner` of `router/scanner.py` builds the `Scanner` again on the next request) is not refused as "busy". A missing overlay still needs a reboot to take effect.

#### Development mode
With `MOCK_HARDWARE=1` (`main_dev.py`) the routers build `hardware.scanner_mock.ScannerMock`, a simulated rig with this class's API, states and status data; see the README.

#### `Scanner(xvs: Optional[bool] = None, camera_mode: Optional[str] = None)`
Initializes motion controllers, safety limit interrupts, LED illumination, and camera mode configuration.
- **`camera_mode` Resolution Hierarchy**:
  1. Explicit `camera_mode` argument (`"rpi_sync"`, `"xvs"`, or `"staggered"`).
  2. Legacy `xvs` boolean flag: `xvs=True` maps to `"xvs"`, `xvs=False` falls back to `CAMERA_MODE` env var.
  3. Environment variable `CAMERA_MODE` (case-insensitive).
  4. Default production fallback: `"rpi_sync"`.

#### `is_streaming -> bool`
Dynamic property returning `True` if `self.dual_cameras` is initialized and actively capturing live frames.

#### `level -> int`
Returns the current elevation slice count during an active 3D scan sequence.

#### `preflight(check_cloud: bool = True, check_tof: bool = True) -> None`
Cloud, ToF and disk checks (see Phase 1). Raises `ScannerPreflightError`. Called by `setup_and_stream()` before the state transition (the face prepare: no ToF, cloud only with `upload_r2`).

#### `require_motors() -> None`
Checks that the Arduino answers (`ArduinoBridge.ensure_connected()`: reconnects when the port is closed or was never opened, then a PING; a transaction already in flight counts as alive) and that both motors are configured (`Motor.configure()` is retried for a motor that is not). Raises `ArduinoUnavailableError` (a `ScannerError` with `unavailable = True`; the routers answer **503**). Called by a scan prepare, `begin_face_scan()`, `POST /scanner/start` and every `/test` motor endpoint (not `/test/cleanup`).

#### `require_tof() -> None`
The ToF check of the object scan (at `/prepare` through the preflight and again at `/scanner/start`): available and a valid test reading, after one `ToFSensor.reinitialize()` when it fails. Raises `ScannerPreflightError` (400). Skipped with `SCAN_PREFLIGHT=0`. The face scan never calls it.

#### `upload_progress() -> dict`
`{"seconds_since_last_upload": float | None, "upload_drain_timeout_s": float}` for `GET /scanner/status`.

#### `ScannerUploadError(ScannerError)`
Raised by `scan()` when photos are missing from the bucket after the drain; `.missing` is the sorted list of cloud keys.

### Lifecycle & Motion

#### `setup_and_stream(enable_stream: bool = True, camera_mode: Optional[str] = None, preflight: bool = True, **kwargs) -> list[str] | None`
Runs the preflight (skipped with `preflight=False`, which the manual `/test/stream/start` and `/test/camera/snap` use: they need no cloud), closes stale cameras, starts camera sensors using the resolved camera driver (`DualCameraRPISync`, `DualCameraXVS`, or `DualCamera`), boots the stream and returns stream URLs (`None` when a cancel landed meanwhile).

#### `finish_preparation(**kwargs) -> None`
Background worker for homing down, the `z_start_mm` climb (default 30 mm), R2 bucket cleanup, thermal stabilization, and in-place camera calibration (with `lock_auto=True`).

#### `motion_guard() -> ContextManager`
Non-blocking, re-entrant (per thread) exclusive right to move the rig. Raises `ScannerBusyError` immediately when another thread holds it. Used by `move_z_up`/`move_z_down`, `home_z_axis`, `move_z_to_top` and the turntable rotation of a ring; external callers (the `/test` router) wrap their own moves in it.

#### Module constants
`Z_TRAVEL_MAX_MM` (the usable Z travel of the rod, set per rig: currently `475`) and `Z_HOMING_MARGIN_MM = 15`: homing and move-to-top are limited to their sum (490 mm = **49000 steps** at 1/4 microstepping, 100 steps/mm). Both live in `hardware/rig_limits.py`; the longest single move a request may ask for (`Z_DISTANCE_MAX_MM` in `schemas/scanner.py`) is the travel itself, 475 mm.

#### `home_z_axis(delay: float = Z_PREPARE_DELAY_S, start_delay: float = 0.004, ramp_percent: float = 0.1, acceleration: bool = False) -> None`
Drives carriage downward until `down_endstop` triggers, for at most 49000 steps (490 mm). The coils are released right away after the endstop STOP (the STOP already disabled the driver, so there is no extra settling pause on that path). The default is constant speed (`acceleration=False`, `delay = Z_PREPARE_DELAY_S = 0.0010`, the same profile as the manual z-move); `acceleration=True` ramps from `start_delay` (`ramp_percent` of the move). The `z_start_mm` climb of `finish_preparation` (default 30 mm) uses the same constant profile. Raises `ScannerError` when the endstop was not reached (aborted or cancelled move, or the travel budget ran out) and `ScannerBusyError` if another motion is in progress; motor/serial errors are propagated, not swallowed.

#### `move_z_to_top(delay: float = Z_PREPARE_DELAY_S, start_delay: float = 0.004, ramp_percent: float = 0.1, acceleration: bool = False) -> None`
Drives carriage upward until `up_endstop` triggers (same 49000-step budget), after which the coils are released (no extra settling pause on this path: the endstop STOP already disabled the driver). Raises `ScannerError` when the endstop was not reached.

#### `move_z_up(steps, delay=0.002, step_type=None, acceleration=False, ...) -> bool` / `move_z_down(...)`
One Z move inside `motion_guard()`, with the endstop protection of its direction. **Constant speed by default** (`acceleration=False`, Z-ACC-2): a ramp is used only when the caller passes `acceleration=True`.

#### `move_z_up_distance(distance: float = 100.0, delay: float = 0.002, ...) -> bool`
Moves carriage UP by distance in millimeters (constant speed unless `acceleration=True`). Blocked if top limit switch is active; `ScannerBusyError` if another motion is in progress; returns `False` (nothing sent) when a cancel applies.

#### `move_z_down_distance(distance: float = 100.0, delay: float = 0.002, ...) -> bool`
Moves carriage DOWN by distance in millimeters. Blocked if bottom limit switch is active; same busy/cancel behaviour as the UP variant.

#### `scan(angle: float = 18.0, delay_turntable: float = 0.0010, z_move_mm: float = 100.0, delay_z_motor: float = 0.0010, turntable_acceleration: bool = True, ..., turntable_end_delay: float | None = 0.015, z_end_delay: float | None = None, finish_state: str = "idle") -> None`
Executes full physical scanning and parallel image upload sequence with independent acceleration profiles and 0.5s motor power settling delays during level transitions, then drains and verifies the upload (see "Mechanical Scan Loop" steps 4-7). Raises `ScannerUploadError` when photos are missing.
* `turntable_end_delay`: step delay (s) at the end of each turntable deceleration (slow stop), clamped to `[0.005, 0.030]`; `None` disables it. Default `0.015`.
* `z_end_delay`: same for the Z-axis; `None` (default) disables it.
* `finish_state`: state left after a scan that completed normally **and was verified** (default `idle`). The state stays `RUNNING` until the drain and verification are done, then goes straight to `finish_state`. The API passes `processing`, so there is no `idle` gap in which a new `/scanner/prepare` could be accepted before the rest of the pipeline runs; that pipeline then moves on at once to `completed` when `cloud.launch_runpod` is `false` (tests only), or runs Turntable Studio on RunPod (`processing` -> `downloading` -> `completed`) when it is `true` (the default). The end-delay tail is dropped automatically when the matching `*_acceleration` is `false`.
* After the `z_start_mm` start-position move in `finish_preparation()` the Z driver is released (the lead screw holds the carriage), so it is not energized at 1.8 A while waiting for `/scanner/start`.
* A climb that ends exactly on the top switch now takes the final top ring; a cancel that tears the hardware down under the scan thread ends the scan quietly instead of raising.
* `move_z_up()` / `move_z_down()` and the `move_z_*_distance()` helpers accept `end_delay` as well (default `None`).

#### Face prepare (`setup_and_stream(scan_mode="face", check_cloud=upload_r2)` + `finish_preparation(z_start_mm, upload_r2)`)
`POST /scanner/face/prepare` runs the same two phases as the object prepare, with these differences:
* the preflight does not check the ToF sensor, and checks the cloud only with `upload_r2`; old R2 job folders are cleaned only with `upload_r2`; every Z move uses the prepare's `z_delay` (default 0.005 s = 2 mm/s, FACE-19; a capture may override it);
* the router checks first that MediaPipe, OpenCV and the face model are there (`Scanner._face_detection_problem()`, 400);
* in position the cameras are **not locked**: `prepare_scan()` without `lock_auto` puts the lenses on the requested focus (an integer or a pair) or the saved one (`"auto"` / `null`), and AE/AWB keep following the subject (manual `exposure_time` / `analogue_gain` / `colour_gains` are not applied yet). The camera settings and `upload_r2` are kept (`_face_camera_settings`, `_face_upload_r2`) for the lock at capture time;
* the state becomes `PREPARED` with `mode = "face"` and `z_position_mm = start_z_mm`.

#### `begin_face_scan(strategy="sweep_best_score", search_range_mm=150.0, step_mm=8.0, manual_z=None) -> None`
Synchronous part of the face capture, called by `POST /scanner/face/capture` before it answers 202: refuses an emergency stop in progress (`ScannerStoppingError`, 409), a run that owns the rig (`ScannerBusyError`, 409), and a scanner that is not `PREPARED` with `mode == "face"` or whose carriage position is unknown (`ScannerModeError`, 400). Validates the heights (`ValueError`, 422: `manual_z` in `150..250`, `z_position_mm + search_range_mm <= 475` for a search, every distance a whole number of Z steps). For a search (no `manual_z`, strategy not `none`) it checks MediaPipe / OpenCV / the model **before anything moves** (`ScannerPreflightError`, 400). Then the Arduino (`require_motors()`, 503) and the state becomes `RUNNING`.

#### `face_scan(strategy="sweep_best_score", search_range_mm=150.0, step_mm=8.0, manual_z=None, settle_s=0.150, finish_state="completed", analyzer=None, begun=False) -> dict`
The face capture, from the prepared height (no homing: the prepare did it).
* **Height**: `manual_z` (direct move), a search (`sweep_best_score`: climbs through `search_range_mm` by `step_mm`, early exit 5 steps after an apex above 1.2; `direct_stop`: stops when both cameras see the nose at $0.45 \le Y \le 0.55$), or `strategy="none"` (photo where the carriage is).
* **Fresh frames** (FACE-16): every evaluation uses `get_latest_lores_frames(fresh=True, strict=True)`: a pair that started after the move ended (the frame in flight is skipped); `FACE_FRAME_ATTEMPTS` (3) waits of `FACE_FRAME_TIMEOUT_S` (1 s) without one end in `ERROR`.
* **Score and no face** (FACE-11): the score of `StereoFramingAnalyzer` (centering, size, cheek profile and the share of the 478 landmarks inside the frame). When no camera saw a face (or the best score is below `FACE_MIN_SCORE`, 0.3) the photo is taken at the start height and the run still ends `completed`, with `face_detected: false`, `best_score: null` and a `warning` (also in `phase_message`). A face seen by one camera only is a warning too.
* **Detector lifetime** (FACE-14): the MediaPipe detector is built for the search only (`with FaceScanner(...)`) and closed after it; nothing stays in memory between scans.
* **Every Z move** goes through `_face_z_move()`: `move_z_*_distance(distance, delay=Z_PREPARE_DELAY_S, acceleration=False)`, the result checked (a move that does not complete is an `ERROR`) and `z_position_mm` updated. `_face_go_to()` always arrives from below (descend past the target by 3 mm, then climb), loading the nut against gravity.
* **Endstops** (FACE-18): only the switch in the direction of the move counts (the move helpers ignore the other one). During the search the top switch ends the search; but the position is then lost (the step stopped somewhere), so the run ends in `ERROR` rather than photographing at a guessed height. On a direct move a switch is an `ERROR` with an explicit message (`top endstop was reached`).
* **Camera lock on the face** (FACE-7b): at the final height `_lock_cameras()` (the same as the object prepare): with `focus="auto"` an autofocus sweep scored on the face box of each camera (`autofocus_roi`, the `bbox_norm` of the best evaluation plus 10 %; the centre box when no face was found), then AE/AWB settle and lock; a fixed focus or manual exposure from the prepare is applied instead of the automatic step. The subject must hold still for the sweep (it stops right after the sharpness peak, so it is shorter than the old full ~10 s sweep; duration not measured on the rig).
* **Capture & upload**: local photo folder wiped, after `settle_s` a synchronized pair `f_{round(z)}.jpg` in `input_images/rig/0/` and `1/`; with the prepare's `upload_r2`, uploaded and verified like the object scan.
* **3D model on the Pi** (`reconstruct`, default on, FACE-20): `hardware/face_reconstruction.py` runs `rpi_face_mesh/reconstruct_3d.py` in a child process on the pair (phase `reconstructing_face`, the step in `phase_message`, killed on a cancel or after `FACE_RECONSTRUCT_TIMEOUT_S`), writes into `results/.<job_id>.partial/` and renames it to `results/<job_id>/` with `status.json` `ok` (so `/library` never lists half a model). The state is `PROCESSING` while it runs; a failure ends the run in `ERROR` (`error` and `face_result.reconstruction_error` set, photos kept).
* **Outcome**: `face_result = {"optimal_z_mm", "best_score", "face_detected", "warning", "photos", "r2_uploaded"}` and the state `finish_state` (`completed`). A failure is `ERROR` with `error`; a cancel `CANCELLED`. A new capture needs a new face prepare.
* The ToF sensor is not used. The turntable is kept disabled.

#### `generate_livestream() -> list[str] | None`
Starts the preview pipeline of the active camera driver and returns its URLs (`/scanner/stream/mjpeg?camera=1|2` for `DualCameraRPISync`).

#### `stop_stream() -> None`
Terminates the preview stream and releases camera hardware locks.

#### `emergency_stop() -> None`
Immediately halts all motion via Arduino `0xFF` abort (sent twice to both motors before any `DISABLE`), cuts coil power, kills lights, closes the cameras and publishes `CANCELLED` (see above). Exception-safe.

#### `cleanup() -> None`
Safe power down of motors and lights without clearing terminal states.

#### `close_hardware() -> None`
Explicitly releases GPIO limits, I2C buses, and calls `bridge.close()` to fire a final `0xFF` emergency stop to the Arduino before releasing the OS serial port.
